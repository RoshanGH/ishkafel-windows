# 自动更新：怎么搭起来，怎么发版

## 为什么要有

发到 0.1.172 已经几十版，每一版都要重新发包、对方重新解压、重新装命令行、
重新换说明书。而**版本对不上是最难查的一类问题**——旧 CLI 调新参数、旧手册
教不存在的命令，都真机撞过，报错都指不到根因上。

让软件自己升级，这三样东西就永远是同一版。

## 一条硬规矩：安装包必须私有存放

产物里 `--dart-define` 注入的 AI 凭据是**明文躺在二进制里**的：

```bash
strings ishkafel.app/Contents/Frameworks/App.framework/App | grep <key 前几位>
```

一抠就有。所以包一旦公开读，谁拿到链接都能提出方舟 key 去烧钱。

因此：**包和清单都存私有 bucket**，由 app 拿一对**只读**凭据现换预签名链接。
泄露的后果被限制在「别人能下载安装包」，而不是「别人能花你的钱」。

长期看真正的解法是凭据不进客户端（加一层自己的服务端代理 AI 调用），
但那是另一件事。

## 一次性搭建

在 `.secrets/` 下建这几个文件（不进 git）：

| 文件 | 是什么 | 谁用 |
|---|---|---|
| `update_tos_region` | 如 `cn-beijing` | 两边都用 |
| `update_tos_bucket` | bucket 名 | 两边都用 |
| `update_tos_endpoint` | 如 `tos-cn-beijing.volces.com` | 两边都用 |
| `update_tos_ak` / `update_tos_sk` | **只读**凭据 | 编进产物 |
| `update_tos_ak_write` / `update_tos_sk_write` | **可写**凭据 | 只发版用，不进产物 |
| `update_tos_manifest_key` | 可选，默认 `latest.json` | 两边都用 |
| `windows_update_signing_private_key` | Windows Ed25519 发布私钥 | 只发版用，不进产物 |
| `windows_update_signing_public_key` | Windows Ed25519 发布公钥 | 编进 Windows 产物 |

**两对凭据必须分开。** app 里那对只给这一个 bucket 的 `GetObject`——
写凭据进了产物，拿到包的人就能往发布目录里塞东西。

Windows 签名密钥用下面的命令初始化一次；工具发现任一文件已经存在就拒绝覆盖：

```powershell
dart run tool/update_signing_key.dart
```

Windows 与 Mac 可以共用 bucket，但 Windows 固定使用 `windows/latest.json` 和
`windows/releases/`。`0.1.237` 仍读取 `latest-windows.json`，但它不认识新清单的
签名信任根，也会拒绝未做 Authenticode 的包，所以发布工具默认不改写旧清单。
只有包具备受信任 Authenticode 时才能显式传 `--publish-legacy-manifest`。
`0.1.238` 是一次性手动安装的引导版，从它之后才具备新信任根。

没配这些文件时，更新功能整个不显示（不能摆一个点下去永远报错的按钮），
打包流程也照常跑，只是不发布。

## 打包 ≠ 上线

这是两件事，**词也要分开用**：

| 词 | 做什么 | 谁做 |
|---|---|---|
| **打包** | 版本号 +1，构建出可安装的产物，放进 `build/dist/` | 开发随时做，做多少次都行 |
| **上线** | 把这一版推到线上，**所有人下次打开就会看到更新提示** | **产品负责人点头才做** |

产物存在 ≠ 用户能拿到。打包是内部动作，上线是对外的动作——一旦推上去，
所有人下次打开就会被提示更新，收不回来。

**不是每一个版本号都要上线。** 中间那些验证用的、只改了日志的、还没验完的，
打包留在本地就行。

```bash
./scripts/pack.sh      # 打包：版本号 +1 → 构建 → 打 zip → 重启本机
./scripts/publish.sh   # 上线：先列出这一版改了什么，问一遍再推
```

上线走 `tool/publish_release.dart`，不依赖 `tosutil` 之类的外部工具——用预签名
URL 直接 PUT，本机装没装都能发。顺序是**先传包、后传清单**：反了的话清单已经
指向新版本而包还没上去，这中间任何人点更新都会下到 404。

## 使用者那边看到什么

设置 → 关于 →「软件更新」：版本号、这一版改了什么、要下多少 MB。
点更新 → 确认（会重启、会打断正在跑的活儿）→ 带进度下载 → 校验 → 重启。

重启后自动做两件这个软件独有的收尾：

- **命令行工具**：`/usr/local/bin/ishkafel` 是个指向 app 内 CLI 的 shim，
  app 换了位置就失效。每次启动都重写一次（幂等、便宜）
- **给 Agent 的说明书**：那是复制出去的文件，不重装永远是旧的。
  只给**装过且过期**的人更新，更新完提示「让 Codex 重新加载一次」

这两条对**手动换包**的人同样生效——不是只为自动更新准备的。

## 替换那一步为什么这么绕

不能在 app 自己的进程里替换自己：正在运行的可执行文件被删掉之后，
后面每一次动态库加载都会失败，崩得莫名其妙。所以交给一个独立的 shell：

```
等旧进程退出 → 旧的改名留着 → 新的就位 → 删掉旧的 → 重新打开
```

中途任何一步失败都把旧的搬回来并照常打开。**绝不能出现「升级把软件搞没了」。**

另外两条也是踩出来的：

- 解压用 `ditto` 而不是 `unzip`——后者丢扩展属性，代码签名跟着失效，
  换上去的 app 一打开就被 Gatekeeper 拦下
- sha256 和签名都在**动现有 app 之前**验。先换后验等于没验

## 真机验证记录（2026-09-02）

整条链路在真机上完整走过一遍，**包括最难的那段：替换正在运行的自己**。

做法：把当时的 0.1.176 复制一份到 `/tmp` 当作「使用者手上的旧版」，
发布 0.1.177，然后启动那份旧版。

| 步骤 | 结果 |
|---|---|
| 旧版启动后自己查到新版本 | 顶栏出现「有新版本 0.1.177」 |
| 点它 | 弹出更新对话框 |
| 下载 → 校验 → 解压 → 验签 | 全过 |
| 替换自己并重启 | 那份 app 的版本号变成 0.1.177，进程跑在新版上 |
| 残骸 | 没有 `.old` 残留 |
| 说明书 | 自动更新到 0.1.177（Claude Code / Codex 两处都是） |

**这一趟抓到一个不跑就发现不了的 bug**：`codesign --verify --deep -q`
——codesign 根本没有 `-q`，它 usage 报错、退出码 2，于是任何包都被判成
「签名验证没通过」，所有人点更新都会失败。而单元测试全绿，因为注入的是
假 runner，我让它返回什么就是什么。

教训写进了记忆：**外部命令的参数必须先手跑一次**。

## 一个自动化上的坑

Flutter 窗口**不吃 System Events 合成的点击**（`click at {x,y}` 没反应），
也不在辅助功能树里暴露按钮。要用 CGEvent 发真实鼠标事件才点得动：

```swift
CGEvent(mouseEventSource: nil, mouseType: .leftMouseDown,
        mouseCursorPosition: p, mouseButton: .left)?.post(tap: .cghidEventTap)
```

坐标要用**窗口位置 + 窗口内相对比例**换算，而且注意截图是 2x Retina 的，
像素坐标要除以 2 才是逻辑坐标。
